# RFC 00044: Vector Actions Settings

```vector-agent-inline-action
label: Start a discussion about this document
prompt-field: prompt-message
profile: code
prompt: prompts-00010-start-discussion-action
input:
  document: rfc-00044-vector-actions-setting
```

```vector-agent-action
label: Create a task
profile: create-doc
prompt: prompts-00005-create-document
input:
  message: Create a task to implement the `rfc-00044-vector-actions-setting`
  document-type: task
  document-name: implement-rfc-00044-vector-actions-setting
```

## 1. Problem

The VS Code extension currently has three action entry points whose execution behavior is fixed by extension code:

1. Creating a governed document from the sidebar form.
2. Running a `vector-agent-action` block from a governed document.
3. Running a `vector-agent-inline-action` block from a governed document.

Projects cannot centrally select the agent profile and prompt used by these entry points. Similar behavior must therefore be repeated in document action blocks or changed in extension code. This prevents repositories from governing action behavior as project configuration and makes action customization inconsistent.

The extension needs a project-level action configuration that can override known extension actions while preserving current behavior when no override exists.

## 2. Proposal

Add `.vector/actions.yaml`. The file contains an `actions` map keyed by action ID. Action IDs are open-ended strings rather than a closed schema enumeration. Each configured action selects an agent profile and prompt and may provide default `input` values for prompt interpolation.

A representative configuration is:

```yaml
actions:
  create-doc:
    profile: create-doc
    prompt: prompts-00005-create-document
    input:
      document-type: "#{doc-type}"

  vector-action:
    profile: code
    prompt: prompts-00011-run-configured-action
    input:
      source: governed-document
```

The initially recognized extension action IDs are:

| Action ID | Trigger | Runtime context |
|---|---|---|
| `create-doc` | The sidebar create-document form is submitted. | `doc-type` contains the selected governed document type. |
| `vector-action` | A block or inline document action is executed. | Every field from the action block is available for interpolation. `file-path` contains the governed document path relative to the `doc` directory, and `file-name` contains only the governed document file name. |

Additional action IDs may appear in the map so future extension features can adopt them without changing the configuration shape. An unknown ID has no effect until an extension entry point invokes it.

### 2.1 Resolution behavior

For each supported entry point, the extension:

1. Resolves its action ID.
2. Looks up that ID in `.vector/actions.yaml`.
3. Uses the existing built-in execution behavior when the file is absent or the ID is not configured.
4. When configuration exists, resolves the configured `profile` against `.vector/agents.yaml`.
5. Merges variables in this order: configured `input` defaults, values supplied by the document action or inline form, and values generated by the extension. Each later source overrides duplicate keys from earlier sources.
6. Builds the prompt selected by `prompt` using one substitution pass over the merged variables. An unresolved placeholder fails the configured action.
7. Presents the agents associated with the resolved profile.
8. Starts the selected agent with the rendered instruction.

This is an override of execution policy, not a replacement for the existing default path.

### 2.2 Document action behavior

A `vector-agent-action` supplies its complete parsed YAML block as runtime context. The extension then adds `file-path` and `file-name`, overriding any same-named values from the action block or configured `input`. If the `vector-action` override is configured, the extension executes the configured action. Otherwise, it executes the block using the current behavior.

A `vector-agent-inline-action` first renders and collects its existing inline UI fields. After the UI resolves, it follows the same `vector-action` lookup and fallback behavior as a block action. The resolved form values are included in the runtime context passed to interpolation.

Both document action forms use the same `vector-action` action ID. Separate IDs may be proposed later if a concrete use case needs different policies.

### 2.3 Create-document behavior

After the sidebar form supplies a document type, the extension looks up `create-doc`. When configured, it exposes the selected type as `#{doc-type}` and follows the configured profile and prompt flow. When no override exists, the extension continues its current create-document workflow.

### 2.4 Compatibility and observability

The feature is backward compatible for repositories without `.vector/actions.yaml` and for action IDs omitted from the file. At load time, the extension validates each configured entry independently and reports every invalid entry. Valid entries remain available. Invoking an ID that is present but invalid fails that action; it does not fall back to built-in behavior or execute a different configured prompt.

The extension should report enough context to diagnose failures: the action ID, the invalid field, and the relevant configuration file. Diagnostics must not include rendered prompt contents or other potentially sensitive runtime values by default.

## 3. Alternatives Considered

- **Extend `.vector/agents.yaml`:** This keeps agent and action configuration in one file, but couples agent definitions to extension UI entry points and makes both schemas harder to evolve independently.
- **Add settings to every action block:** This supports document actions but cannot govern sidebar actions centrally and duplicates policy across documents.
- **Hard-code a closed action ID list in the schema:** This improves typo detection but requires schema and extension changes for every new entry point. An extensible map better matches the intended plugin-like behavior.
- **Remove the built-in fallback:** This provides stricter governance but breaks existing repositories and turns optional customization into a mandatory migration.

## 4. Tradeoffs

| Pro | Con |
|---|---|
| Centralizes project-specific action policy. | Introduces another configuration file and validation surface. |
| Preserves current behavior when no override exists. | Fallback behavior can hide misspelled action IDs unless diagnostics cover unused entries. |
| Supports future action IDs without changing the root schema. | Open-ended IDs reduce static validation. |
| Reuses existing agent profiles and prompt interpolation concepts. | Action and extension values override configuration defaults; configuration authors must not treat `input` as enforced policy. |
| Gives inline and block document actions one governance path. | Shared policy may be too coarse for repositories that later need separate inline and block behavior. |

## 5. Acceptance Criteria

- [ ] The extension loads optional `.vector/actions.yaml` configuration.
- [ ] The root `actions` value is validated as a map keyed by non-empty action IDs.
- [ ] Each configured action validates its required `profile` and `prompt` settings and its optional `input` map.
- [ ] `create-doc` overrides sidebar create-document execution and receives `doc-type`.
- [ ] `vector-action` overrides both block and inline document action execution.
- [ ] Document actions expose the complete parsed action YAML plus `file-path` and `file-name`.
- [ ] Inline actions collect their UI values before the configured action is executed.
- [ ] Variable merge order is configured `input`, action or inline form values, then extension-generated values; each later source overrides duplicate keys.
- [ ] Extension-generated `file-path` and `file-name` override same-named values from both configured `input` and document actions.
- [ ] Prompt variables use hash-brace syntax, are replaced in one pass, and unresolved placeholders produce an actionable failure.
- [ ] Missing configuration or a missing action ID preserves current behavior.
- [ ] Invalid entries are diagnosed independently at load time; valid entries remain available, and invoking an invalid configured ID fails without fallback.
- [ ] Tests cover absent files, unknown IDs, invalid profiles, invalid prompts, partial invalid configuration, duplicate variable keys, single-pass interpolation, unresolved variables, document path metadata, inline form values, and fallback behavior.
- [ ] User documentation includes the schema, recognized IDs, runtime variables, and an end-to-end example.

## 6. Decisions

1. **Variable precedence:** Configured `input` supplies defaults. Action block or inline form values override those defaults. Values generated by the extension override both sources, including for `file-path` and `file-name`. The configured `profile` and `prompt` remain action settings rather than mergeable input variables.
2. **Invalid configuration:** Validate entries independently at load time and surface all diagnostics. Valid entries remain usable. An ID present with an invalid entry fails when invoked and never falls back to built-in behavior.
3. **Interpolation:** Replace variables in a single pass. Do not recursively expand replacement values. Reject unresolved placeholders with an actionable error.
4. **Document action ID:** Both block and inline actions resolve `vector-action`. Distinct IDs are deferred until a concrete need arises.

## 7. Staff Engineering Assessment

The variable precedence contract is now explicit: configuration defaults yield to action values, and extension-generated values always win. This prevents a document action from spoofing extension-generated source metadata. The configured `profile` and `prompt` must be read from the action settings, never from the merged variable map.

Implementation should keep parsing, validation, action resolution, interpolation, and agent launch as separate components. The remaining gaps are schema documentation, path normalization across platforms, and negative tests for malformed or adversarial YAML values. A schema version is not yet justified because the file is new and unshipped, but the parser should reject unknown settings within a configured action so future schema evolution remains deliberate.
